# Architecture and extension boundaries

`feedback/api.py` handles HTTP routing, validation, session/Bearer transport, and response schemas. `feedback/services.py` authorizes participants/managers and filters representations. `feedback/storage/base.py` defines the persistence contract. `feedback/storage/relational.py` shares the application operations and portable SQL; `sqlite.py` and `postgres.py` own provider connections, dialect-specific queries, constraints and migrations. SQL and driver types stay inside `feedback/storage`. `feedback/webhooks.py` performs signing and network delivery. `feedback/web` is plain HTML/CSS/JavaScript and changes state exclusively through `/api/v1`.

The factory accepts a storage configuration, opens SQLite (the default) or PostgreSQL, including Supabase database connections, and manages webhook, push, embedding installation, crawling, ingestion, authoring and AI-chat workers when workers are enabled. Production runs one HTTP process/container with one local volume. PostgreSQL stores application records remotely, while setup state and optional model weights remain local. There is no database query in an HTTP handler or application service. SQL-free domain values are dictionaries, stable application-generated UUID strings, actor records, and UTC ISO-8601 timestamps. Scheduling uses Unix seconds internally; HTTP representations convert delivery scheduling timestamps to the same UTC ISO-8601 format as other resource timestamps.

## Atomic operations

SQLite connections enable foreign keys, WAL, FULL synchronous durability, and a ten-second busy timeout. Connections and transactions are short-lived. Each write uses `BEGIN IMMEDIATE` so external identity find/create, votes, setup, creator edits/deletes, and moderation serialize their state checks with mutations. `accepted_at` is also protected by a database trigger. Optimistic versions prevent an editor from overwriting a change they have not seen.

PostgreSQL keeps the same single-writer semantics with a transaction-scoped advisory lock acquired before authorization reads. Read transactions use a repeatable, read-only snapshot. Connections set the private `supaknock` search path and bounded lock/statement timeouts. Database triggers preserve immutable fields and records. The adapter uses parameter binding, translates only parameter markers, and reports safe storage errors rather than driver details. Opaque external IDs use UTF-8 bytes in PostgreSQL so embedded NUL characters and exact byte distinctions remain intact.

Every material request mutation records an immutable JSON event and any subscribed webhook job in the same transaction. A webhook configuration update is serialized with event creation. Destinations and encrypted signing secrets are copied into jobs. Deleted requests have no foreign-key cascade into events; their original snapshots remain available in delivery inspection. Votes cascade only for eligible request deletion. Project and board deletion are intentionally absent. Migration 021 adds reversible [project/board archiving](archiving.md), local immutable archive audit records and transactional activity gates; it never rewrites request events or delivery snapshots.

Delivery claiming is a transaction that chooses a due queued job or expired lease, increments its attempt count, and assigns a unique lease token. Completion updates match that token: an abandoned worker cannot overwrite a newer worker’s result. A lease lasts 60 seconds; transport uses ten-second socket timeouts. One delivery thread processes jobs serially. HTTP is at-least-once: a crash after receiver success and before recording success causes a duplicate with the same event ID.

## Identity and permissions

A native account uses a normalized email and Argon2id hash in `local_credentials`; a user can exist without those rows. External identities preserve IDs byte-for-byte as decoded JSON strings, with uniqueness on `(project_id, external_user_id)`. Concurrent first use creates exactly one mapping and user. There is no implicit linking by email/name/ID across projects.

Sessions and project credentials are cryptographically random and stored as SHA-256 hashes. Session CSRF tokens are also hashed; the browser receives an independent readable CSRF cookie and sends it as a header. Cookie mutation authentication verifies both the token and the configured Origin. Regular signup forbids unknown fields, including `role` and internal user IDs.

Project credentials can act only within their project. `participate` resolves an external user for a specific operation. `manage` allows board management, request content/moderation/lifecycle, queue/history, webhook configuration and delivery administration. Creating projects, native admins, or API credentials is native-admin-only. `audience:read` exposes current notification identities. `manage` does not imply `audience:read` or `participate`. Public reads through credentials require `read` or `manage`.

Public representations include only approved request data, a creator display name when present, vote counts/state, and limited acceptance/status history. Full private history and moderation reasons require the creator or management access. Voter identities never appear in public responses. Native users have no automatic external identity.

## Operations and expansion

Migrations serialize through SQLite locking or a PostgreSQL advisory lock, apply ordered scripts transactionally, and roll back on failure. PostgreSQL also records migration checksums and refuses a changed applied script. A database newer than the application stops startup. There is no erase/rebuild fallback. Backup uses the SQLite online backup API or a PostgreSQL custom archive of `supaknock`, together with the effective application secrets. PostgreSQL maintenance refuses an absent or outdated schema instead of initializing it. Restores use a new destination and preserve the original installation.

The owner has authorized PostgreSQL and Supabase installation storage. [Provider configuration](database-providers.md) covers connection URLs, TLS, private-schema permissions and explicit encryption keys. SQLite remains the default; switching a provider does not transfer data or enable multiple instances. Other adapters, a general management CLI, MCP, organizations, custom lifecycle workflows and attachments remain outside this release. The independently deployed push relay retains its own PostgreSQL storage.

The iPhone application is an API client, with administrator bearer sessions separate from browser cookies and project credentials. Future client surfaces reuse the API. The implemented [connected-app feature](connected-apps.md) is a read-only HTTP connection to app-owned data, separate from installation database configuration.

## Optional push and live chat

`feedback/push.py` owns relay enrollment, protected credential handling and bounded outbound transport. The configured storage adapter atomically snapshots eligible admin recipients alongside request events or chat messages. Current session, role, preferences and randomized registration generations fence delivery and cancellation. The independent relay uses Supabase PostgreSQL for credentials, quotas, cancellation records and APNs jobs; installations using SQLite or standalone PostgreSQL do not depend on Supabase.

`feedback/chat.py` and `chat_api.py` expose anonymous visitor access, authenticated customer access, and native administrator chat. `chat_customers` owns conversations and read positions independently of temporary sessions. External customers reuse project-scoped user mappings; native customers use their existing account. Anonymous customers retain only their original private credential, with no public recovery or implicit linking. Migration 006 preserves existing visitor histories, read positions and idempotent message IDs.

Trusted `participate` backends or native account sessions exchange for one-hour hashed customer credentials. Browser credentials bind an allowed origin; native credentials require no Origin. Each operation rechecks the customer/project, expiry, revocation and issuing API key or native session inside its storage operation. Renewed credentials resolve the same customer and share unread state and message retry identity. Native logout/password change and project-key revocation invalidate derived access. Customer credentials cannot administer chat or access other customers.

WebSockets use short-lived one-time tickets in the first frame and recheck authorization. Committed sequences provide reconnect catch-up and idempotent message writes. Each newly committed message atomically records a body-free `chat.message_created` event and subscribed webhook job using the existing delivery infrastructure, alongside eligible admin push jobs. Retried messages produce no second event. There is no delivery-order guarantee; event IDs deduplicate notifications and per-conversation message sequences order history.

All SQL remains in the storage package. The widget remains plain JavaScript in Shadow DOM, with explicit project origin allowlists. Guest-to-account linking is deferred. See [chat](chat.md), [push](push.md) and [contracts](push.md).

## Private connection metadata

`feedback/client_ip.py` validates the ASGI client address after the server's explicitly configured trusted-proxy handling; HTTP handlers attach it to Actors/chat principals, and WebSockets use the current connection rather than the ticket issuer's address. Migration008 stores request creation, request-event and message IPs outside immutable webhook payloads. Conversation initial IP is immutable; each new customer message updates the latest customer IP, while admin replies and retried messages do not. State frames refresh on both moderation version and message sequence, keeping connected administrators' details current.

`account_activity` records account creation and successful session issuance in their respective transactions. It survives session deletion and offers deterministic bounded pagination guarded by a live native-admin session. Services/output views omit IP fields for public users, owners, project credentials and chat customers. Delivery payloads remain unchanged. See [capture, proxy configuration and retention](operations.md#private-connection-metadata).

## Shared admin notification inbox

`NotificationService` authorizes native administrators through a transport-independent session contract. The storage adapter rechecks the session transactionally, records notifications alongside request/chat events, and stores one shared read timestamp per event. Sequence watermarks make “Mark all read” safe against later arrivals. Web and Swift clients consume the same API; this inbox has no relay dependency and does not change per-admin chat read positions. Migration007 backfills outstanding event-backed work once. See [notification contract](notifications.md).

## Optional AI support and current authoring

AI runtime/generation/knowledge/authoring/chat modules are separate application services with configured-database persistence and fenced workers. Provider credentials live in the native-admin account library with explicit project/role bindings and per-project models; exact capability evidence and shared quota cooldowns are distinct. Local model weights live on the existing volume, outside image layers. Knowledge originals, local indexes, authoring checkpoints, reviewed article provenance and chat/report receipts remain in the configured database. SQLite uses its existing FTS/vector indexes; PostgreSQL computes lexical and cosine candidates over the same bounded, authorized corpus without requiring pgvector.

Project AI administration is embedded in project settings. Knowledge uses Library/Sources/Drafts; recoverable source-wide authoring creates private drafts and only explicit human approval creates an independently indexed article. The anonymous widget uses one conversation timeline for messages and confirmed-report review, with compact expandable citations. See [account keys](ai-web-admin.md), [AI administration](ai-web-admin.md), [authoring](ai-authoring-contract.md) and [widget contract](ai-widget-contract.md). Earlier design plans describe historical checkpoints; current implementation/evidence takes precedence over stale future-tense wording.

## Connected-app read boundary

`connected_apps_protocol.py` owns the versioned bounded wire models, `connected_apps_api.py` native-admin transport, `connected_apps.py` authorization/receipt/capability orchestration, and `connected_apps_transport.py` public HTTPS I/O. Migration 019 persists only configuration, encrypted credentials, identity/link approvals, display timezone and metadata audit. Read transactions snapshot authority before network work and recheck it before returning. A cancellable child process bounds DNS/TLS/body time; the parent enforces installation/per-connection concurrency and a bounded queue. No remote network work occurs inside a storage transaction.

Web `connected-feed.js` and native `ConnectedFeed.swift` merge streams in active view memory using microsecond and UTF-8 order. Wrapped continuations bind current native session, app/project, connection generation, query, expiry and random process epoch. No browse-session table, stored remote payload, event ingestion or automatic remote polling is introduced. The frozen [protocol](protocol/v1/README.md) replaces the earlier planning-only extension description.
