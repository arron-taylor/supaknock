# Customer AI and human chat

Public read-only MCP tools and per-message podcast context are implemented as an optional extension. See [Connected AI tools and episode chat](mcp-tools.md) for setup, compatibility, source snapshots and widget examples. Customer-specific MCP grants remain deferred.

The supplied widget remains anonymous. It uses the existing website chat session, approved origin, short-lived chat credential and durable conversation. It does not inspect a host website's login, accept an external customer ID, link guest history to an account, or receive a project credential. Authenticated custom clients continue to use the existing customer chat API.

## Support choice and conversation recovery

Public chat configuration exposes whether AI is explicitly enabled and ready. Ready projects show a choice between AI and a person; other projects retain the human-only message flow. Selecting support or sending a message starts a session. Loading the widget does not create a session or invoke a model. Direct human controls remain independent of assistant tool flags.

Mode changes use the current conversation's `mode_version`. The widget identifies AI messages explicitly, renders bodies and source excerpts as text, and displays server-returned citations. Source links accept only absolute HTTP(S) URLs without embedded credentials and open with `noopener`, `noreferrer`, and no referrer. Uploaded documentation has no invented public URL. Waiting, failed, cancelled, closed, expired and unavailable states have explicit copy. Terminal provider failure normally causes the server to transfer the conversation to waiting for a person independently of the assistant handoff tool; the widget explains that transition. If the customer explicitly returns to AI with a failed turn, Use last question again fills the editor for a separate deliberate send. It never silently creates another turn.

The widget stores only the anonymous token, its expiry, and the conversation ID under a server/project/website-origin-specific local-storage key. HTTP requests omit cookies and use `X-Chat-Token`; native sign-in cannot silently become chat identity. Reconnect restores messages after the durable sequence cursor and retrieves current drafts and receipts. Unsent text survives ordinary transport failures, and retrying the same message retains its client message ID. Ending a chat uses an inline confirmation explaining that access to guest history and report status will be lost while submitted reports remain.

## Draft review and submitted receipts

The single conversation timeline loads private drafts and receipts through separately paginated APIs (25 per page), placing their cards beside the originating message using the server-provided `message_sequence`. There is no separate Reports tab. A card expands for exact review/editing/submission or receipt details without leaving the conversation. All mutations use `/api/v1`; the scoped routes and server-side authority checks are described in [the tools contract](ai-tools-contract.md).

A draft review shows the exact title, description, destination board, pending moderation visibility, expiry, guest tracking notice and current feedback-page link. Customers can edit, copy or cancel eligible drafts. Saving a draft does not submit it. A separate, explicitly labelled Submit action first reloads the draft and compares its content, version, hash, destination, expiry, notice and current permissions to the displayed review. Any change requires another review; the final request sends the exact version and hash with a stable confirmation ID. A previously confirmed draft opens its existing receipt rather than creating another request.

Guest submission disabled states retain the copy and actual feedback-page actions. Copying transfers no data to that destination. The server's pre-submit notice explains how to submit under an account on the feedback page; the widget never promises account claiming or email updates. Post-submit notices describe private guest access accurately. Both draft and receipt links use the server's current flow override, project URL or native-board fallback; the client adds no identity, secret, draft text or invented custom request path. Accepted reports retain custom destinations.

Receipts show current moderation and lifecycle separately from draft state. Eligible creators may edit or delete an unaccepted report with its current version. Deletion uses an inline impact confirmation and preserves the private tombstone. A non-null `accepted_at` permanently removes creator edit/delete controls, even if the report's later status changes. Server conflicts remain visible and preserve unsaved edits; refreshing an edited review explicitly confirms discarding those edits.

## Updates, focus and presentation

An open chat refreshes drafts and receipts after messages, WebSocket ready/state notifications, reconnect and its own mutations. A five-second bounded poll also observes other-tab edits and administrator moderation, which need not create chat messages. Public readiness is refreshed at most once per fifteen seconds by that poll. Hidden documents skip periodic reads; closing the panel clears its polling/reconnect timers and closes its socket. An already dispatched request may finish, but closing does not start new recurring work or model calls.

Unchanged mode controls and report lists retain their DOM nodes and keyboard focus. Unedited receipts can update automatically; a changed draft or an edited receipt displays a conflict notice without replacing edited fields or silently accepting new submission content. The welcome screen uses the configured project title and places the initial AI/person choice together. After selection, a compact strip above the conversation retains the support controls, including a visible human-support option while talking to AI. Chat options holds the AI explanation and end-chat action, the launcher is hidden while open, and the rounded composer provides a spacious writing area and grows for longer drafts. Review cards use inline confirmation instead of blocking browser dialogs; dynamic content remains text. Source references use a collapsed Sources disclosure, numbered cards with website/domain or document attribution, and Read more / Show less for long excerpts. Disclosure and review controls remain keyboard-accessible. The existing appearance API, automatic/light/dark themes, reduced motion and mobile layout remain available.

## Host-owned presentation

The existing embed JSON/manual mount accepts `presentation: bubble|bar|inline` and optional `revealAfterScroll` document pixels for floating launchers. Defaults preserve existing embeds. Inline places only the launcher at the target div and ignores the scroll threshold. Its conversation opens as a fixed overlay (using the top layer where supported), bottom-right on desktop and almost full-screen on mobile. The launcher remains in flow while open, avoiding layout shifts; closing returns focus without scrolling the page. Reveal is once per mount, never takes focus, and is bypassed by explicit `open()`. Layout never changes session scope, identity, support modes, business hours, report confirmation, or send-time session creation. See [chat integration](chat.md#choose-a-layout-and-scroll-reveal).
